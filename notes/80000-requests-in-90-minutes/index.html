80,000 requests in 90 minutes: what the agent found that pentests missed

A free account became a foothold in under two hours. The flaw was one missing authorisation check, not a model.

Twinthos · Published 27 November 2026 · 27 November 2026 · 4 min read

THE SHORT ANSWER

In brief

An agentic penetration-testing tool sent more than 80,000 requests in 90 minutes against a developer-tools company and found one missing authorisation check that earlier human penetration tests had missed, including one the week before. The attacker signed up for a free account at 05:59 UTC and had deployed a backdoor service in the company's cloud project by 07:59. The vendor's own AI agent refused every attempt to extract secrets through planted prompt-injection pages. The UK's National Cyber Security Centre warned on 24 November that agentic attack frameworks are doing this to UK organisations now.

The 90 minutes

Dosu, a developer-tools company, published its postmortem on 8 November 2026. An attacker used ARTEX, an open agentic penetration-testing framework, against its systems on 2 November. The agent sent more than 80,000 HTTP requests in roughly 90 minutes.

The root cause was one incorrect row-level security check on organisation invitations, in code written years earlier by humans. Several penetration tests had passed over that code, including a test commissioned the week before the incident. The agent did not find something new. It found something repeatedly, at a volume no human test reaches.

The two hours

The attacker created a free account at 05:59 UTC. The last recorded action in the vendor's cloud project was at 07:59 UTC, under two hours later. In between, a backdoor service was deployed inside that cloud project.

Dosu has not disclosed how many user records were taken. It has stated that names, email addresses, sign-in providers and sign-in times were downloaded. Under UK GDPR, that combination of fields is personal data, which means a UK business in the same position would be assessing a reportable incident rather than a technical one.

What the agent refused

The attacker then planted pages containing prompt injection and asked Dosu's own AI agent for secrets, environment variables and cloud metadata. The agent refused every request and returned no credentials.

That is the detail most vendors would not publish. An agent defending a system held the line against an agent attacking it, on the same day, in the same codebase. Dosu's own conclusion is the line worth repeating: the logs indicate the attacking agent believed it was running a penetration test, and had it been trained with malicious intent the outcome would have been worse.

What actually failed

On 24 November the National Cyber Security Centre published its warning about agentic cyber attacks. Since September 2026 it has recorded a marked rise in attacks using frameworks including ARTEX, Cairn, PentAGI, RedAmon, Xalgorix and Darkmoon. Its explicit finding: none of the weaknesses being exploited are new.

The weaknesses it lists are familiar ones — credentials committed to repositories, infrastructure-as-code misconfiguration, default credentials, unauthenticated APIs. These are Cyber Essentials territory, not frontier-model territory. What changed is the speed between discovery and exploitation, and the fact that the discovery is now automated and cheap.

IN PRACTICE / WHAT THE RECORD SHOWS

What the record shows, and what it does not

The published sequence is unusually complete for a company of this size: a sign-up timestamp, an exploitation window, a service deployed in a cloud project, and a stated count of customer fields taken. The gaps matter too. The postmortem does not put a number on affected accounts, and it does not name the cloud provider. A reader can verify the shape of the incident but not its size.

For a UK supplier, the practical consequence is that this incident is reportable the moment names and email addresses leave the building, whether or not the origin was an AI framework. The mechanism is new; the obligation is not.

THE OPERATING DECISION

Four questions before you let an agent hold credentials

First, which accounts can that agent act as, and what is the blast radius of each. Second, what stops it acting on records belonging to another tenant, and when was that control last tested by someone trying to break it. Third, what the agent is allowed to read from the environment — secrets, metadata, file system — and whether that permission is necessary. Fourth, who reads the logs, and how long after the action.

If any answer is 'the vendor handles it', the answer is no. The vendor in this case had a functioning defence in one place and a missing check in another, which is what every real system looks like.

DIRECT ANSWER

Could an AI agent really find a vulnerability in our systems that our supplier missed?

It found one in this case, in code that several human tests had passed, including one the week before. The honest reading is narrower than the headline: an agent does not reason better than a good tester, it simply tries far more combinations in the same hour, and it does not get bored. Anything reachable by an authenticated request is in scope, whether or not a human thought to look there.

THE PRACTICAL TEST

Write down every account an agent can act as, every record it can reach, and every secret it can read. Then ask who is testing that list against an automated attacker, and when. If the answer is a penetration test from last year, the list is a hypothesis.
