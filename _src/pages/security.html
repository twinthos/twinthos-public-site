An unsafe instruction in an email. A connector with too much access. A failed run that looks successful. AI security starts with these concrete failure paths.

01 / ACCESS

Constrain the tools.

Define accounts, data, permitted actions and approval points. Separate reading a record from changing or exporting it.

02 / TESTING

Challenge the instructions.

Test hostile content, missing context, tool failures and attempts to cross the agreed scope. A prompt alone is not a security boundary.

03 / EVIDENCE

Make failure visible.

Keep useful activity records, record incomplete coverage and define who investigates, stops or recovers a failed workflow.

ATTACK SURFACE / WHAT GOES WRONG

Untrusted content
tries to become authority.

  • Instructions hidden in an email, web page or repository issue
  • A misleading tool description or connector permission
  • Incorrect or poisoned knowledge used later as a fact
  • An agent with more privilege than its task needs

DEFENSIVE ENGINEERING / WHAT WE TEST

The action must
stay inside its job.

  • Separate data from trusted instructions
  • Allow specific tools, accounts and destinations
  • Require human review for sensitive decisions
  • Record decisions, failed checks and incomplete coverage

WHAT THE EVIDENCE CAN SHOW

Source code & tests

Review the actual implementation and current CI results.

Explicit coverage

Unavailable feeds and incomplete scans must remain visible. No findings does not mean no risk.

Deployment verification

A passing test suite does not prove a production daemon is running or that alerts reach their destination.

The review should
leave you with answers.

AI security engagements are scoped separately. We agree the systems, access, tests and deliverables before work starts.

What can the agent reach?

Inventory its tools, accounts, data and outward connections, including Model Context Protocol (MCP) servers where used.

What can trigger an action?

Trace instructions from people, documents, websites and tool responses. Identify where untrusted content could influence decisions.

What happens when it fails?

Review approvals, logs, alerts, retries and stop procedures. Separate measured results from assumptions.

What should change first?

Prioritise findings with evidence, practical fixes and retesting steps. Define the remaining limitations.

DATA & RESPONSIBILITY

Document the details.

Before deployment, agree which data is accessed, where it is processed, who can see it and how long it is kept. Third-party model, tool and hosting providers have their own terms and controls.

Human approval, least privilege and monitoring reduce risk; they do not make an agent impossible to break. We do not claim blanket compliance or independent certification.
